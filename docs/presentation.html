What We Built

A fully virtualized sovereign tenant cluster where every component runs inside a KubeVirt VM.

Layer 1: Control Plane VM

  • RHCOS VM with bridge binding on management cluster
  • Runs full HyperShift control plane (40+ pods)
  • etcd, kube-apiserver, router, ignition-server
  • Auto-proxy forwards traffic to bridge pods

Layer 2: Worker VMs

  • Created by HyperShift NodePool + CAPK
  • Boots RHCOS, fetches ignition, MCD firstboot
  • Registers with tenant kube-apiserver
  • Runs tenant workloads (pods)

Traffic Flows

1. External → Tenant API (kubectl from laptop)

Client → OCP Route → HAProxy → Proxy EndpointSlice → CP VM :6443 → socat → kapi pod

2. Worker VM → Tenant API (kubelet registration)

Worker VM → OCP Route → HAProxy → Proxy EndpointSlice → CP VM :6443 → socat → kapi pod

3. Worker VM → Ignition (bootstrap config fetch)

Worker VM → OCP Route → HAProxy → Proxy EndpointSlice → CP VM :9443 → socat → ign-proxy pod

4. Bridge pods → Cluster Services (DNS, API inside VM)

bridge pod → DNAT iptables → ClusterIP → endpoint pod (same-node preferred)

The Core Problem: Bridge Pod Reachability

KubeVirt VMs with bridge binding get a routable pod IP. But pods inside the VM use a separate bridge CNI that is invisible to the management cluster's OVN network. 

  Management Cluster OVN Network (10.128.0.0/14)
  ┌────────────────────────────────────────────┐
  │  All pods, services, routes — routable     │
  │  CP VM pod: 10.129.x.x  ← REACHABLE      │
  └──────────────────┬─────────────────────────┘
                     │
                     ✖ THIS BOUNDARY IS THE PROBLEM
                     │
  ┌──────────────────▼─────────────────────────┐
  │  VM Internal Bridge Network (10.244.0.0/24)  │
  │                                            │
  │  kapi:      10.244.0.29   ← NOT REACHABLE │
  │  router:    10.244.0.48   ← NOT REACHABLE │
  │  ign-proxy: 10.244.0.30   ← NOT REACHABLE │
  │  etcd:      10.244.0.12   ← NOT REACHABLE │
  └────────────────────────────────────────────┘

  Current workaround:  socat on VM pod IP → bridge pod IP
  Proper fix:          Make 10.244.0.0/24 routable from cluster

Path Forward: Eliminating the Socat Hack

Option A: VXLAN Tunnel Near-term — 1-2 weeks

  Management Cluster Node                  CP VM
  ┌────────────────────────┐              ┌────────────────────────┐
  │                        │              │                        │
  │  vxlan100              │← VXLAN →│  vxlan100              │
  │  10.244.0.254/24       │  (UDP 4789)  │  10.244.0.1/24         │
  │                        │              │  (bridge gateway)      │
  │  route 10.244.0.0/24   │              │                        │
  │  → dev vxlan100       │              │  kapi: 10.244.0.29     │
  │                        │              │  etcd: 10.244.0.12     │
  └────────────────────────┘              └────────────────────────┘

  Eliminates: socat proxy, proxy EndpointSlices, DNAT sync
  • Add VXLAN interface via ignition systemd service
  • One tunnel per CP VM, simple point-to-point
  • Bridge pods directly reachable from management cluster
  • No external dependencies

Option B: BGP-EVPN via OVN-K Route Advertisements Long-term — proper solution

  Management Cluster                        CP VM
  ┌────────────────────────────┐           ┌────────────────────┐

  │  import 10.244.0.0/24     │           │  10.244.0.0/24     │
  │  via VM pod IP             │           │                    │
  │                            │           │  EVPN VXLAN:       │
  │  All nodes learn route     │           │  L2 segment stretch │
  └────────────────────────────┘           └────────────────────┘

  Eliminates: ALL proxy workarounds
  Enables: multi-CP-VM scaling, live migration
  • Uses OVN-K RouteAdvertisements + FRR-k8s (available today)
  • OKEP-5088 (EVPN) could stretch L2 segment natively
  • Standard DC networking — BGP+EVPN is the modern fabric
  • Production-grade, scalable to many tenants
